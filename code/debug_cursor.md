# Debug Investigate Loop（排障协作）

## 风格

- 优先用用户语言；回复短、直接。
- 先给结论（1–2 句），再给证据。
- 用户复述理解（「我理解是…」）时：先判 **对 / 部分对 / 反了**，再展开。
- 机制与复述未对齐前不急着改代码（除非用户明确要求现在就修）。
- 不做用户已否决的范围外改动（禁止顺手重构、顺手加功能）。

## 协作习惯（出现则适配）

1. **机制先于结论** — 调用链、谁在等谁、每个旋钮含义。
2. **数字例子** — 用真实规模（batch、并发、step 指标）举例，不只讲符号。
3. **旋钮极性** — 「更早 / 关掉 / 加量」常与数值方向相反；必须写清「值↑ ⇒ 什么变」。
4. **谱系对比** — 被要求时用表格对比路径 A vs B（开关、提交、提前返回、步边界、同步）。
5. **风险 → 代码** — 设计讨论后用「有 / 部分 / 刚修 / 管不住」回答「考虑到了吗」。
6. **A/B 思维** — P0 之后给可测的一旋钮实验。

## 流程

跟踪：

```
- [ ] 1. 分类症状
- [ ] 2. 证明目标路径已开启
- [ ] 3. 说清本意收益（跳过了哪段等待/工作）
- [ ] 4. 读代码里真实控制流顺序
- [ ] 5. 用日志/指标/时间戳对照「本意 vs 实际」
- [ ] 6. 拆开账本 vs 墙钟
- [ ] 7. 对齐复述；修正拟议配置的极性
- [ ] 8. 最小修复（P0）→ A/B 验证
```

### 1. 分类症状

| 类型 | 典型信号 |
|--|--|
| Hang / 调度不起 | 资源池、actor create 卡住、RPC 永久等待 |
| 结果错误 / 污染 | 半组入训、半截当完成、过期 ID |
| 功能开了但无收益 | 指标「看起来健康」，step 耗时≈基线 |
| 配置幻觉 | CLI/env 设了但未进运行时；字符串 `"False"` 仍为真 |

### 2. 证明路径 ON

- 追踪：启动参数 → 配置合并 → 运行时 resolved dump → 应走的类/分支。
- 列出功能生效时**必须变化**的指标；若从不变化，路径关闭或被旁路。

### 3–5. 本意收益 vs 代码 vs 日志

始终分开：

- **账本**：本步消费/训练/提交了哪些单元（计数可以看起来正确）。
- **墙钟**：本步是否仍在等待本该 defer/跳过的工作。

账本正常却无收益时，重点查 **反模式**：

- 提前返回 / 异步采样后，又对同一批残留做满量 drain/wait
- 门闩把 hold/park 的工作算进 pending，堵住下一阶段（sync / sleep / release）
- 旋钮 A > 0 旁路旋钮 B（必须写明旁路关系）

每条判断要落到代码顺序 + 日志行（或缺什么证据就直说）。

### 6. 分支 / 方案对比

对比实现时用一张表：

开关 · 预填 · 提交 · 提前返回 · 步边界 · 同步/收尾 · 重叠从哪来

同一产品名、不同配置根时要点明。

### 7. 配置建议（必须做极性）

每个旋钮一行：

```
NAME = V  →  含义；↑/↓ 效果；注释与数值是否一致；是否旁路其他开关；是否真正接到运行时
```

注释与数值矛盾的配置直接否定。A/B 每次只改一个行为维度。

### 8. 先修再测

- **P0**：去掉抹掉本意收益的那一步；保留正确性门闩（破坏性 sync 前 abort/必要 drain、更新权重时的 admission）。
- **P1+**：仅在用户要求时做（流水线深度、warmup、额外重叠）。
- 告诉用户下一轮成功应看到哪些日志/指标签名。

## 输出模板

**复述确认**

```
结论：对 / 部分对 / 反了
纠正：（若需要，一句话）
机制：（最短因果链）
```

**风险覆盖**

| 风险 | 代码有吗 | 位置 / 缺口 |
|--|--|--|

**A/B**
